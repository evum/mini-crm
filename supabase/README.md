# База данных mini-crm

## Применение

В `migrations/` оставлена одна миграция:
[`20261105153930_baseline_with_current_data.sql`](migrations/20261105153930_baseline_with_current_data.sql).
Она создаёт схему приложения и восстанавливает снимок текущих данных проекта.

Состав: 4 пользователя Auth и их email identities, 4 профиля, 3 стройки,
10 задач, 31 событие истории, 29 публичных и внутренних функций, индексы,
политики RLS, триггеры и разрешения. Сохранены исходные UUID, даты, комментарии, статусы и идентификаторы истории. Счётчик истории восстановлен выше её последнего ID.
Загрузка снимка происходит до создания прикладных триггеров; ограничения и
внешние ключи действуют, а после загрузки установлена обычная защита истории.

Миграция предназначена для **нового проекта Supabase** с готовой управляемой
схемой `auth` и без прикладных таблиц/пользователей с такими ID. Это не установка
Supabase на обычный PostgreSQL. Выполните её целиком в SQL Editor от имени
`postgres` либо примените через Supabase CLI к новому проекту. Все операции
выполняются в одной транзакции. Повторное применение к заполненной базе запрещено.

## Пароли при восстановлении

В снимок не включены пароли, их хеши, access/refresh tokens, сессии и ключи
проекта. По умолчанию аккаунты создаются без пароля; вход по паролю станет
доступен после его установки через Supabase Auth Dashboard / Admin API.
Существующие пароли исходного проекта остаются действующими в исходном проекте.

Чтобы сразу включить вход в новой базе, при выполнении миграции в SQL Editor
сразу после её `begin;` добавьте настройку только в запускаемую копию:

```sql
select set_config('crm.bootstrap_password', '<новый пароль не короче 16 символов>', true);
```

Так задаётся одинаковый начальный пароль для четырёх восстановленных аккаунтов, с отдельным bcrypt-хешем на каждый. Не сохраняйте запускаемую копию с паролем в репозитории. Настройка действует только в транзакции миграции. Сессии не переносятся: в новом проекте нужно войти заново. Настройки Supabase Auth, внешних провайдеров, Storage и API-ключи не являются частью этой миграции.

Security Advisor отмечает семь публичных RPC с `SECURITY DEFINER`. Это намеренная
граница записи: прямой DML закрыт, функции проверяют пользователя и полномочия, имеют фиксированный `search_path`, а `anon` не имеет права вызова.
Объяснение проверки: https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable

В Data API оставьте схему `public`; **не добавляйте `crm_private`** в exposed
schemas. Клиент читает таблицы через RLS, записывает данные только через RPC.
Технические функции и прямые изменения таблиц для `anon`/`authenticated` закрыты. Владельцы базы и серверные секреты считаются доверенными администраторами.

**Отдельно отключите открытую регистрацию в настройках Supabase Auth.**
SQL-миграция не меняет настройки сервиса Auth. Отключите также анонимный вход, если он включён. Во фронтенде допустим только публичный ключ проекта; серверные секреты и `service_role` нельзя сохранять в репозитории или клиентском коде.

## Пользователи

Создайте пользователей вручную в Supabase Auth, затем добавьте профили через
SQL Editor. Роль не берётся из пользовательских metadata. Автоматического
создания профиля нет: пользователь без активного профиля не видит данные.

```sql
-- Замените UUID на ID пользователя из Supabase Auth.
insert into public.profiles(id, full_name, role)
values ('UUID-ИЗ-AUTH', 'Имя пользователя', 'dispatcher');
-- Для исполнителя используйте role = 'executor'.
```

Один пользователь имеет одну роль. Все постановщики управляют всеми объектами
и задачами. Исполнитель назначается при создании задачи и должен быть активным.
Для блокировки пользователя администратор задаёт `profiles.is_active = false`.
Ссылки на пользователей сохраняются, поэтому удаление пользователя Auth,
связанного с профилем, запрещено внешним ключом; используйте блокировку.

## API

Baseline включает девять функций чтения с `SECURITY INVOKER`; они применяют RLS
и не дают клиенту дополнительных прав.

Чтение: `profiles`, `objects`, `tasks`, `task_status_history`.
Список профилей содержит только необходимые приложению поля, без email/пароля.
Исполнитель видит свой профиль и профили авторов/участников истории своих задач.

RPC (имена аргументов важны для `supabase.rpc`):

- `create_object(p_name, p_address)` → объект.
- `update_object(p_object_id, p_name, p_address)` → объект.
- `delete_object(p_object_id)` → мягкое удаление объекта и его задач.
- `create_task(p_object_id, p_title, p_description, p_assignee_id)` → задача.
- `update_task(p_task_id, p_object_id, p_title, p_description, p_assignee_id)` → задача;
  передаются все редактируемые поля, статус не меняется.
- `delete_task(p_task_id)` → мягкое удаление задачи.
- `change_task_status(p_task_id, p_expected_status, p_new_status, p_comment = null)` → задача.

Статусы: `new`, `in_progress`, `in_review`, `accepted`, `rework`.
Проверяется строго заданный граф переходов и роль текущего пользователя.
Возврат в `rework` требует непустого комментария. Автор, время и история
задаются базой. При создании фиксируется событие `NULL → new`.

Ошибка `40001` означает конфликт со сменой статуса/переносом задачи: обновите
данные перед повторной попыткой. RPC блокируют строки на время транзакции;
изменение статуса и запись истории атомарны. После переназначения прежний
исполнитель теряет доступ к задаче и её истории.

Удалённые данные скрыты от обеих ролей; физически история остаётся в базе.
Восстановление и физическое удаление не предоставляются через API.
